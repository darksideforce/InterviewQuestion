8： **React 的生命周期有哪些阶段？在 Function 组件中如何使用 `useEffect` 模拟生命周期？**
- 挂载阶段：**`componentDidMount`**组件创建dom，收集依赖
- 更新阶段：**`componentDidUpdate`**组件的props或者state改变时触发
- 销毁阶段：**`componentWillUnmount`** 组件销毁
注意这些周期只存在class组件内，函数类组件没有，函数类组件使用useEffect来取代
- useEffect：useEffect(fn, []) 代表组件被创建
- useEffect：useEffect(fn, [deps])代表组件被更新
- useEffect：使用useeffect返回的函数做取消回调

9： **什么是 React Hooks？为什么使用 Hooks 时不能在条件语句或循环中调用？**

 React Hooks 底层依靠**单向链表和严格固定的调用顺序**来匹配状态； 为了**确保每次渲染时 Hooks 的调用顺序和数量绝对一致**，绝对不能把 Hooks 写在 `if` 条件句、`for` 循环或嵌套函数中。否则会出现严重的运行错误或者渲染错误。
 
10: **`useState` 的状态更新是同步还是异步的？什么是批处理 (Batching) 机制？**

批处理：react会将同一批多次状态更新合并为同一个，也就是更新队列

16： **React 常见的性能优化手段有哪些？（请从渲染、加载、组件设计等维度回答）**

我一般不会一上来就把所有地方都加上 `useMemo`、`useCallback`，而是先用 React DevTools 的 Profiler 看提交次数和耗时，确认瓶颈是在重复渲染、计算、网络请求，还是资源加载，再针对性处理。

- **渲染层面**：首先保证列表的 `key` 稳定，避免因为 key 变化导致组件反复卸载和重建。对于 props 没变化但会被父组件带着刷新的子组件，我会用 `React.memo`；如果传给它的是对象、数组或者函数，再根据实际情况配合 `useMemo`、`useCallback` 保持引用稳定。计算量比较大的筛选、排序也可以用 `useMemo` 缓存，但简单计算没必要缓存，因为缓存本身也有成本。
- **大数据量场景**：长列表我会用分页、虚拟列表，只渲染可视区域；搜索输入会做防抖，请求支持取消，并且避免旧请求晚返回后覆盖新结果。对于输入框这类高优先级交互，也可以用 `useDeferredValue` 或 `useTransition` 把非紧急更新延后，先保证输入响应。
- **加载层面**：路由和体积较大的组件通过 `React.lazy`、动态 `import` 和 `Suspense` 做按需加载；图片做懒加载、压缩并设置合适尺寸；接口层面减少重复请求，对可复用的数据做缓存。另外还会结合构建产物分析，检查是否引入了过大的依赖、是否能做 tree shaking。
- **组件设计层面**：我会把状态尽量放在真正需要它的组件附近，避免父组件一个状态变化带着整棵子树更新；Context 也会按业务拆分，不能把所有全局状态放进一个 Provider。组件拆分要看更新频率和职责，不是拆得越细越好。稳定内容可以通过 `children` 或组件组合隔离，表单里也尽量避免每输入一个字符就刷新整个页面。

所以我的思路是先定位，再从减少渲染次数、降低单次渲染成本、减少首屏资源这三个方向处理，最后再用 Profiler 和实际数据验证优化有没有效果。

17：自定义的hooks你用过哪些？

我在项目里封装过的自定义 Hook，主要是把重复的状态和副作用逻辑抽出来，不是单纯把几个函数包一层。比较常用的有：

- `useRequest`：统一管理请求的 `loading`、`data`、`error`，支持手动触发、参数变化重新请求和取消请求。组件卸载时会通过 `AbortController` 取消请求，同时会处理竞态问题，避免旧请求后返回覆盖新请求。
- `useDebounce`：用于搜索框和筛选条件，把防抖定时器、清理逻辑封装起来。这里会注意依赖变化和闭包问题，组件卸载时也会清理定时器。
- `usePagination`：封装页码、每页条数、总数和重置逻辑。比如筛选条件改变时页码要回到第一页，避免每个列表页面重复写这一套逻辑。
- `usePermission`：根据当前用户的权限标识判断按钮或操作是否可用。Hook 只负责返回权限结果，具体是隐藏按钮还是禁用按钮由组件决定，避免权限逻辑和 UI 强耦合。当然，前端权限只控制展示，真正的安全校验仍然要由后端完成。

我判断要不要抽自定义 Hook，主要看一段逻辑是否被多个组件复用，或者单个组件里的状态、副作用已经比较复杂。自定义 Hook 复用的是逻辑，不会共享同一份 state；每次调用都有自己独立的状态。封装时我也会尽量保持输入、输出清晰，避免做成一个参数很多、职责很重的“万能 Hook”。

18：hoc组件有没有封装过自定义的组件

封装过。之前做过一个权限控制类的 HOC，例如 `withPermission`，它接收一个业务组件和权限标识，先读取当前用户权限，有权限时渲染原组件，没有权限时返回空内容或者无权限占位。原组件本身不需要知道权限数据从哪里来，只关注自己的业务展示。

实现时我会注意几个问题：第一，剩余的 props 要完整透传给原组件；第二，如果外部需要拿到原组件的 ref，要配合 `forwardRef` 继续透传；第三，要设置可读的 `displayName`，方便在 React DevTools 里排查；另外 HOC 不会在组件的 render 过程中动态创建，否则每次都会生成新的组件类型，导致子树卸载重建。

HOC 比较适合权限、埋点、错误兜底这类需要包裹组件的横切能力。不过在函数组件项目里，如果只是复用状态和副作用逻辑，我现在会优先用自定义 Hook，因为组件层级更扁平，数据来源也更直观。HOC 我主要保留在确实需要控制“组件是否渲染”或者兼容已有代码的场景里。
